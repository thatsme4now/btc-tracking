PART A

Setup & Price

Every mempool-based feature in this app — price, historical price fill, address tracking, TXID jump-links — needs a configured mempool instance first. Everything in this section is off until you set it up.

ℹ Self-hosted only, not mempool.space: the app talks to your own mempool instance (e.g. the mempool app on your Umbrel, or any instance on your LAN) via plain host:port — it does not call the public mempool.space API directly. If you don't run one yet, the Umbrel Community App Store described on the Usage / Setup page is one way to get one.

Configuring the instance

Open the gear icon in the header → Settings → section “Mempool integration (optional)”.

FieldMeaning
HostHostname or IP of your mempool instance, e.g. localhost or a LAN IP. No scheme (no http://).
PortPort your mempool instance listens on.
Left emptyAll mempool features stay disabled — nothing is ever called until both fields are filled.
🔒 Privacy: this app's own server — not your browser — connects to the configured host. Use your local network only; don't point this at a public instance you don't control.

Current price & historical price fill

Once configured, three places start using it:

  • Header price badge — the small mempool icon next to the price fetches the current rate for your display currency directly from your instance.
  • Holdings view — “Fill missing years from mempool (EUR+USD)” backfills missing year-end reference prices from your instance's historical series.
  • Yearly view — “Fill missing months from mempool (EUR+USD)” does the same per month.
ℹ Historical fill only covers EUR and USD — other display currencies aren't backed by a historical series and must be entered manually. A data point only counts if it's close enough to the target date (year-end / month-end); otherwise that period is left unfilled rather than showing a misleading estimate.

Mempool clock (Holdings view)

The Holdings view also gets a small “Mempool” tile with a live next-block fee/clock visualization, embedded from your configured instance — with an “open in new tab” shortcut. It uses the same host/port, no extra setup.

PART B

Addresses & On-Chain Balance

Attach one or more Bitcoin addresses to a position (wallet/exchange) to compare its tracked BTC amount against what's actually on-chain — without leaving the app.

Adding an address

Open a position for editing → section “Bitcoin addresses” → enter the address (e.g. bc1q…) and an optional label, then “Add address”.

Fetching a balance

Each address has “View balance” / “Fetch”. The first fetch calls your mempool instance and caches the full result — confirmed balance, unconfirmed balance, and up to 50 recent transactions. Opening the dialog again shows this cached snapshot instantly, with the time of the last fetch (“Last fetch”) — no network call until you explicitly refresh.

FieldMeaning
Confirmed balanceOn-chain balance from confirmed transactions only.
UnconfirmedNet effect of transactions still in the mempool, shown separately.
Received / SentDirection and net amount of each of the up-to-50 recent transactions.
Already trackedMarked live against your current transaction list — never cached, so it can't go stale.
ℹ “Never fetched” is shown until the first fetch — click “Fetch” for the current on-chain state. After that, re-fetching is always your choice, so this feature never calls out on its own.

Address overview (all addresses at once)

For a position with multiple addresses, “Address overview” opens all of them together, instantly from cache. A separate “Refetch all (live)” button triggers a fresh call for every address in one go.

On-Chain column in the positions table

The Data Management table has an “On-Chain” column, computed purely from the cached balances above — no network call on page load. Click a value to jump straight into that position's address overview.

StateMeaning
–Position has no addresses attached.
⚠ partialNot every address has been fetched at least once — the shown sum only covers the ones that have.
highlightedOn-chain sum differs from your tracked BTC amount for this position — worth a look, even while partial.
PART C

Link & Import

When a fetched on-chain transaction isn't tracked yet, you get two ways to handle it — depending on whether it's genuinely new or already recorded without a TXID.

Linking to an existing transaction

For every not-yet-tracked, confirmed transaction, the app searches your existing TRANSFER_IN/TRANSFER_OUT transactions on the same position for a match: no TXID set yet, exact same BTC amount, same calendar day as the on-chain transaction. A match shows “Possible existing transaction found” with a “Link” button.

  1. Click “Link” on the matching candidate.
  2. Only the on-chain TXID is set on your existing transaction — amount, date, position and everything else stay exactly as you entered them.
  3. If several candidates match, all of them are listed — pick the right one yourself.

Importing as a new transaction

No match, or none of the candidates are right? “Import anyway” creates a brand-new TRANSFER_IN/TRANSFER_OUT transaction with the on-chain TXID already set.

ℹ Matching is intentionally narrow: only TRANSFER_IN/TRANSFER_OUT, only the same position, exact amount, same day. It's meant to catch the obvious case — an on-chain move you already logged by hand before adding the address — not to guess across ambiguous situations.
PART D

TXID in the Edit Dialog

Every TRANSFER_IN/TRANSFER_OUT transaction has an optional on-chain TXID field in its edit dialog — set automatically by linking/importing above, or entered manually.

FieldMeaning
On-chain TXID64-character hex TXID. Soft-validated only — a value that doesn't look like a valid TXID shows a warning but is still saved as entered.
Jump buttonOpens the transaction directly in your configured mempool instance. Disabled if no instance is configured.

Self-transfer pairs

A transfer between two of your own positions is physically one on-chain transaction, stored as a linked TRANSFER_OUT/TRANSFER_IN pair. The TXID field keeps both sides in sync:

  • Setting a TXID on one leg fills the other leg automatically — but only if it's still empty there. A differing value on the other side is never silently overwritten.
  • Clearing a TXID on one leg clears it on the paired leg too, unconditionally — so removing a mistaken TXID always removes it on both sides of the pair, in one edit.
ℹ This sync only runs on save, and only between the two legs sharing the same transfer — unrelated transactions are never touched.
